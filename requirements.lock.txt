# =============================================================================
# VERSIONS EXACTES — l'empreinte d'une installation qui marche.
#
#   requirements.txt        les planchers, lisibles par un humain
#   requirements.lock.txt   ce qui est réellement installé, figé
#
# CE QUI POSE LES DÉPENDANCES, ET CE QUI NE LES POSE PAS
# -----------------------------------------------------
# `bootstrap.sh` (étape 5) et `make venv` installent `requirements.txt`, PAS ce
# fichier. Ce fichier n'est donc pas ce qui rend une installation reproductible :
# c'est ce qui permet de DIRE si deux installations sont la même, et de figer
# la vôtre quand vous en avez besoin.
#
#   pip install -r requirements.lock.txt      # reproduire exactement cet état
#   diff <(.venv/bin/pip freeze) requirements.lock.txt   # suis-je dessus ?
#
# Régénéré par :  .venv/bin/pip freeze > requirements.lock.txt
#
# CE QU'IL NE FAUT SURTOUT PAS Y OUBLIER
# --------------------------------------
# Une dépendance présente dans `requirements.txt` et absente d'ici produit une
# panne qui ne ressemble pas à une dépendance manquante. `python-multipart` a
# manqué : le cockpit démarrait, `/cc/healthz` rendait 200, `provisioned` était
# vrai — et toute connexion rendait 500 en texte brut, sans une ligne de
# journal. Le nom du module importé (`multipart`) diffère du nom de la
# distribution (`python-multipart`), ce qui rend l'absence encore plus
# silencieuse. Après toute modification de `requirements.txt`, régénérez ce
# fichier depuis un venv REFAIT à partir de `requirements.txt` — pas depuis
# celui que vous aviez déjà, qui contient peut-être ce que vous cherchez à
# vérifier.
